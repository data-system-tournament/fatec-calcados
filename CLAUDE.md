# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

FATECalçados loyalty program (Desafio de Inovação Data System 2026): a Django + PostgreSQL backend and a React + Vite frontend with five tabs: PDV/Caixa (point of sale), Dashboard, Clientes, Vendas and Ações. Code, identifiers, API fields, commit messages and docs are in Brazilian Portuguese. Follow that convention.

## Commands

Everything runs through Docker Compose from the repo root:

```bash
docker compose up -d --build
docker compose exec backend python manage.py migrate
docker compose exec backend python manage.py popular_dados       # deterministic seed; --clientes/--compras/--meses/--semente
docker compose exec backend python manage.py expirar_pontos      # expire overdue point lots
docker compose exec backend python manage.py criar_admin --usuario gerente --nome "Gerente"   # store staff login (/admin/entrar) + Django admin; asks for the password; --redefinir changes it
docker compose exec backend python manage.py criar_cliente --cpf 390.533.447-05 --nome "João Lima" --numeracao 40   # client login (/login), same rules as /cadastro (services.criar_acesso)

# Backend tests (Django TestCase, in backend/src/tests/)
docker compose exec backend python manage.py test
docker compose exec backend python manage.py test src.tests.test_regras
docker compose exec backend python manage.py test src.tests.test_regras.RegrasPurasTest.test_prata_bonus_de_10_porcento

# Frontend (run in frontend/)
npm run lint     # oxlint
npm run build    # tsc -b && vite build
npm test         # vitest run (pure logic + API mappers with mocked fetch)
```

- UI: http://localhost:5173/ (store area, reached only by typing the URL: `/admin` → `/admin/pdv`, `/admin/dashboard`, `/admin/clientes`, `/admin/vendas`, `/admin/acoes`, `/admin/avaliacoes`, `/admin/estoque`; client area: `/login`, `/cadastro`, `/loja`, `/minha-conta`) · Django admin: http://localhost:8000/admin/ (a different thing: the Vite proxy only forwards `/api`)
- The frontend container keeps `node_modules` in the named volume `frontend_node_modules`, which `--build` does not refresh. The compose `command` handles this: on start it compares `package-lock.json` with `node_modules/.lock-instalado` and runs `npm ci` only when they differ. After changing dependencies, `docker compose restart frontend` is enough. It stays inline in the compose file (not a `.sh`) because `core.autocrlf=true` would give a script CRLF line endings.
- Never run `docker compose down -v`: it deletes the `db_data` volume.
- The frontend tests (Vitest, Node environment) cover pure logic (`regras.ts`, `utils/`, `pages/dashboard/csv.ts`, each test next to its file) and the API layer: `src/testes/api.test.ts` runs every `services/api` function against a fake `fetch` (`testes/apiFalsa.ts`, `simularApi`/`chamada`) fed with mocked responses in `src/testes/dados/`. The fixtures are typed with the exported `Api...` types, so `tsc -b` flags them when the API contract changes; when a backend field changes, update the `Api...` type, the fixture and the test together. There are no component tests.
- The Vite dev server in Docker does not see deleted or renamed files: after renaming a module (`x.js` → `x.ts`), `touch` the files that import it or run `docker compose restart frontend`, or the browser keeps requesting the old name (404).

## Backend architecture (`backend/src/`, a single Django app)

The layers are strict, and each one only calls the layer below it:

- `regras.py`: every number from the program rules (tiers, bonus %, 100-point redemption blocks worth R$ 5,00, 12-month validity) as pure functions with no DB access. A rule change starts here.
- `services.py`: the only place where rules touch the DB (`registrar_venda` → `registrar_compra`, `expirar_pontos`, `saldo`, `nivel_atual`, `cadastrar_cliente`). Business violations raise `RegraViolada`, and views turn it into a 400 with `{"erro": ...}`.
- `indicadores.py` (dashboard queries), `acoes.py` (manager action lists) and `consultas.py` (client/sale lists, client profile, sale detail) are read-only. They never write, not even point expirations: `consultas.py` computes the balance from the still-valid lots instead of calling `expirar_pontos`.
- `views.py`: plain Django function views returning JSON under `/api/...`. `/api/clientes/` and `/api/vendas/` serve both GET (list) and POST (register). The client list (`consultas.listar_clientes`) is ordered by balance, highest first, unless `?ordem=nome`. Customer CPFs are always masked (`cpf.mascarar`) in lists, ranking and profile; clients are identified there by `id` (`/api/clientes/<id>/perfil/`). They parse input and call services/indicadores. No business logic goes here.

Key invariants:
- **Points are a ledger.** `MovimentoPontos` rows (accrual, redemption, expiration) are the source of truth. The balance is always their sum, and there is no stored `saldo` field. Each purchase creates a lot that expires after 12 months, and redemption consumes lots FIFO (`_consumir_lotes`).
- The tier comes from points **accrued over the last 12 months**, not from the balance. The bonus uses the tier from *before* the purchase. Points are computed on the amount paid after the discount, with cents dropped.
- The seed (`popular_dados`) creates sales and pushes each one through the same `registrar_venda` that the POS uses, in chronological order. It never writes points directly, and it must stay that way so the dashboard numbers match the rules (checked in `tests/test_telas.py`). Reviews go the same way: ~30% of sales with CPF queue a review a few days later (heap by date, processed between sales) through `services.avaliar_produto`. It also sets each shoe's size grid (`NUMERACOES`) and the product descriptions (`DESCRICOES`).
- **API docs**: `backend/src/openapi.json` is a hand-written OpenAPI 3.1 spec (no DRF, so nothing generates it), served at `/api/openapi.json` with Swagger UI at `/api/docs/` (`views.api_openapi`/`api_docs`, open). `tests/test_openapi.py` fails when a route or method in `urls.py` isn't documented. When an endpoint or its fields change, update the spec and regenerate `docs/endpoints-da-api.pdf` with `node docs/gerar-pdf-endpoints.mjs` (headless Chrome/Edge).
- The user-facing command reference is `docs/comandos.md` (Portuguese); keep it in sync when a management command changes.
- `POST /api/vendas/` is idempotent on the client-generated UUID `id`: a resend returns 200 with the existing sale. Prices always come from the DB. The client sends only `sku`, quantity and `numeracao` (shoe size; `null` for accessories). `data` may come from the register for offline sales.
- **Product reviews (`Avaliacao`)**: a client reviews each product they bought (at a register or online) once and earns `regras.PONTOS_POR_AVALIACAO` (20) as a normal `ACUMULO` lot with no `compra` (12-month validity, FIFO redemption, counts toward the tier). Rating 1–5 and a comment of at least `COMENTARIO_MINIMO` (20) characters (`regras.problema_da_avaliacao`); `services.avaliar_produto` locks the client and a DB unique constraint keeps one review per client and product. `Avaliacao.movimento` points to the lot (PROTECT), so the seed deletes reviews before movements. Profile movements carry `avaliacao` (product name) so statements show where the points came from. API: `GET/POST /api/conta/avaliacoes/` (session), read side in `consultas.avaliacoes_do_cliente`, which also returns the rule numbers so the front doesn't copy them. The manager sees them at `/admin/avaliacoes` (`pages/avaliacoes/AvaliacoesLoja.tsx`, `GET /api/avaliacoes/` → `consultas.avaliacoes_da_loja`): summary, distribution and per-product average cover every review, while the `produto`/`nota` filters (in the URL) only narrow the paginated comment list.
- **Stock by size**: no per-store split. Shoes (`Produto.usa_numeracao`) keep stock per size in `EstoqueNumeracao` (unique product + `numeracao`; the rows are the product's size grid) and their total is the sum, computed in `consultas._estoque_do_produto`; accessories (sock, insole) use the single `Produto.estoque`. `estoque_minimo` is per size for shoes (seed: `regras.ESTOQUE_MINIMO_POR_NUMERACAO`). Every sale item carries `numeracao`, required for shoes and forbidden for accessories (`regras.problema_da_numeracao`), and it must exist in the grid; `ItemCompra.numeracao` stores it. `registrar_venda` subtracts from that size (or the product) with `F()` clamped at zero (`_baixar_estoque`); the register **never refuses a sale** for lack of stock (the pair is already in the client's hands, and offline sales arrive later), but the online store does: `comprar_online` passes `conferir_estoque=True`, which sums the order per size and locks the rows (`_conferir_estoque`), after the idempotency check so a resend still returns the sale. Status: `regras.situacao_do_estoque` per size/accessory (0 = `ESGOTADO`, up to the minimum = `ACABANDO`, above = `OK`) and `regras.situacao_da_grade` per shoe (all zero = `ESGOTADO`, any size at/below the minimum = `ACABANDO`). The manager counts one size (or the accessory) at `/admin/estoque` (`pages/estoque/Estoque.tsx`: summary cards, color legend, each shoe with its colored size grid, click a size to edit; `POST /api/estoque/<sku>/` {quantidade, minimo, numeracao?} → `services.ajustar_estoque`, which can open a new size, and answers with the list row from `consultas.estoque_de_um_produto`); the list (`GET /api/estoque/?situacao=` → `consultas.estoque_da_loja`) puts out-of-stock and low items first, shows units sold in the last 30 days and counts zeroed sizes (`numeracoes_esgotadas`). Status colors live in `components/ui/situacaoDoEstoque.ts` (Estoque, POS size picker, product page). The catalog (`GET /api/produtos/` → `consultas.catalogo`, open like before) carries stock, the size grid and the review average; the Django admin edits the grid inline.
- **Account deletion (LGPD)**: `POST /api/conta/excluir/` {senha} → `services.excluir_conta` **anonymizes** instead of deleting (sales and the ledger point to the client with PROTECT, and sales must be kept): expires overdue lots, cancels the remaining points as `EXPIRACAO` (balance 0, open liability drops), replaces name/CPF with `regras.NOME_DE_CONTA_EXCLUIDA` and `cpf_de_conta_excluida(id)` (`X` + id, never a real CPF, so the person can sign up again from scratch), clears size/birthday/consent, deletes the `User` and sets `Cliente.excluido_em`. `indicadores.pontos_12m_por_cliente` (base of client lists, ranking, levels) and the `acoes.py` lists skip `excluido_em`; past sales stay in the dashboard unlinked; reviews stay, signed "Cliente excluído". Front: "Excluir minha conta" card + password modal at the end of `MeusDados`. Public page `/privacidade` (`pages/inicio/Privacidade.tsx`, linked from `/cadastro`, the landing footer and Meus dados) describes what is actually collected, the legal bases, cookies (only `sessionid`/`csrftoken` + localStorage, so no consent banner; add one if analytics/ads cookies are ever introduced) and how deletion works; update it when data collection changes. The DPO e-mail is `PRIVACY_EMAIL` in `config.ts`.
- **Store staff login (`/api/equipe/`)**: every store route (dashboard, ações, clientes, vendas, avaliações, estoque) is wrapped in `views._so_equipe` and returns 401 without a logged-in `is_staff` user; only `/api/produtos/` stays open because the online store uses it. Staff are plain Django users created by `manage.py criar_admin` (`services.criar_administrador`: staff + superuser, all-digit usernames refused because client usernames are CPFs, no overwrite without `--redefinir`, client users can't be promoted). Login is `POST /api/equipe/entrar/` → `services.autenticar_equipe` (rejects non-staff); `GET /api/equipe/` returns the user and sets the CSRF cookie. Client and staff share the Django session, so logging in as one in a browser logs out the other. Store tests log in with `tests/apoio.entrar_como_equipe`.
- Registers are identified by `Caixa.codigo` (for example `araras-01`).
- Admin views for `Compra` and `MovimentoPontos` are read-only (`SomenteLeitura`).
- **Client area (`/api/conta/`)**: login is CPF + password, no e-mail. `Cliente.usuario` is a OneToOne to a Django `User` whose username is the CPF (it only holds the password hash). `services.criar_acesso` creates the `Cliente` for a new CPF (store "Loja Online") or links an existing one only if the first name matches. Passwords use Argon2id with the OWASP minimum parameters (`src/hashers.py`, `PASSWORD_HASHERS` in settings; the PBKDF2 hashers stay for old hashes, which Django upgrades on the next login): Django's default PBKDF2 took ~1.9 s per login in the container, this ~70 ms. `Login`/`Cadastro` pass the account the login returns in the navigation state (`{ conta }`), and `ContaProvider` shows it at once while it refreshes in the background. Online purchases go through `services.comprar_online` → the same `registrar_venda`, on the register `online-01` (`caixa_online()` creates it lazily because the seed wipes stores); the CPF always comes from the session, never from the body. These views use the session cookie, so they are **not** `csrf_exempt` (nor are the store routes): the front sends `X-CSRFToken` and `CSRF_TRUSTED_ORIGINS` lists the Vite origins. The account data is `consultas.painel_do_cliente` (read-only); `services.alterar_senha` (`POST /api/conta/senha/`) needs the current password and keeps the session; the frontend has no screen for it for now. The client fills in only `numeracao` (shoe size, 16–48), `nascimento` and the contact consent (`POST /api/conta/perfil/` → `services.atualizar_perfil`, limits in `regras.problema_do_perfil`); consent is stored as `contato_autorizado_em` (LGPD proof: re-checking keeps the date, unchecking clears it). These fields are part of `perfil_do_cliente`, so the manager's client profile shows them too; the seed leaves them empty. The painel also carries `avaliacoes_pendentes` (count, points, latest purchase) for the notifications. The seed deletes client users with the clients.

## Frontend architecture (`frontend/src/`)

- React Router (`routes/index.tsx`, `createBrowserRouter`). `/` is the public landing page (`pages/inicio/Landing.tsx`, fixed palette from the logo `public/fatec-icon.svg` (vinho `#8F0D0D`, cinza `#B7B7B7`) scoped by `.landing` in `index.css`, outside the theme tokens; its rule numbers are copied from `regras.py`, so update it with them). Its hero (`VitrineTenis.tsx`, state in `hooks/useVitrine.ts`) rotates Unsplash sneaker photos listed in `pages/inicio/fotos.ts`; each entry carries the photo's studio background color, which the hero paints behind it. The access screens `/login` and `/cadastro` (`TelaAcesso`, classes `.landing .landing-acesso`; `/login` and `/cadastro` pass `fundoSecreto` (`FUNDO_SECRETO` in `fotos.ts`, the photo `public/fundo-tenis.jpg`) for the minimal frame: a card centered on an empty white screen (always light via `.landing-branca`, no theme toggle); a full-bleed sneaker photo sits under `components/ui/InkReveal.tsx` (21st.dev), a canvas in the background color where the pointer carves wobbly ink stamps that grow and fade) use role tokens (`--l-fundo`, `--l-texto`, `--l-linha`…) that get a light version under `.landing-acesso` following the same `data-theme`/`fatec:tema` choice (toggle `pages/inicio/BotaoTema.tsx`); the landing itself stays fixed. The app screens sit under `layouts/MainLayout.tsx`, which renders the sidebar (`components/layout/Sidebar.tsx`, routes listed once in `navegacao.ts`), a header with the collapse button and the `<Outlet />`; Ctrl/⌘ K opens `SearchPalette` (screens + client search). Pages live in `pages/<area>/`. Everything is TypeScript (strict): pages and components are `.tsx`, hooks and services `.ts`.
- Pages unmount when you leave their route, so cross-page state lives in providers mounted by `MainLayout` (`contexts/`). Each context is split into a `.ts` file (context + hook) and a `*Provider.tsx` file, so the component files only export components (oxlint `only-export-components`).
  - `CaixaProvider` / `useCaixa()`: online flag, the sales queue and the in-progress sale (cart, client, payment, points). The queue is persisted in `localStorage` (`fatec:vendas`) and pending sales are resent on load and on reconnect, which relies on backend idempotency by `id`. A sale is cleared from the context as soon as it is recorded, so a finished cart can't come back.
  - `AcoesProvider` / `useAcoes()`: action lists and which ones were marked as done (the nav badge uses it).
  - `ToastProvider` / `useToast()`: `notify(message)`.
- Client area, organized like online stores (Mercado Livre, Shopee): `/login` and `/cadastro` (`pages/inicio/`, shared frame `TelaAcesso`) sign the client in and land on `/loja` (products). `layouts/ClienteLayout.tsx` (no session → `/login`) renders the same `Sidebar` and header as `MainLayout` with `GRUPOS_CLIENTE` from `navegacao.ts`: "Loja online" (`/loja`, `/loja/carrinho`) and "Minha conta" (`/minha-conta` "Meu perfil": profile header plus tabs `Pontos` (`MeusPontos`), `Extrato` and `Meus dados` (`MeusDados`: shoe size/birthday/consent form plus read-only personal data; unsaved edits are kept in `sessionStorage` (`fatec:rascunho-perfil:<id>`) so leaving the tab, e.g. to `/privacidade`, and coming back keeps them; the page shows a "Complete seu perfil" notice while size or birthday is missing); the tab lives in the URL hash (`#pontos`, `#extrato`, `#dados`) and the old `/pontos` and `/dados` URLs redirect there; `/minha-conta/compras` keeps its own screen). Tabs use the shared `components/ui/Abas` (WAI-ARIA, arrow keys), also used by `MinhasCompras`. Pages are in `pages/conta/` (`Loja` reuses `pdv/ProductGrid` with `variante="loja"`, which renders the storefront cards `conta/CardProduto` (product photo from `Produto.foto` via `pecas.FotoDoProduto`, which falls back to the category icon on the `--foto` token when there is no photo or it fails to load; the review thumbnails use it too; the seed gives every product a free-license Unsplash photo (`FOTOS` in `popular_dados`; the sneakers reuse the landing's) except Palmilha Gel, whose photo comes from Pixabay (full URL in `FOTOS`, since Unsplash has no free insole photo); real review average, "+N pts" from `estimatePoints`, "Tem o seu nº 40" from the profile size, sold-out/last-units badges; photo and name link to the product page, and a shoe's button opens it too because the size is chosen there) while the POS keeps the compact card (with the stock count); shared pieces in `pecas.tsx`). **Product page** `/loja/produto/:sku` (`pages/conta/Produto.tsx`, `GET /api/produtos/<sku>/` → `consultas.detalhe_do_produto`, open): photo, rating, price, points, size radios (profile size preselected, sold-out sizes struck through), stock line, quantity capped by stock minus what is already in the cart, "Adicionar ao carrinho", Descrição/Avaliações tabs (reviewer first name only, "Cliente excluído" for anonymized accounts) and "Você também pode gostar" (same category). The online cart item is `{sku, size, quantity}`; cart operations shared with the POS are in `utils/carrinho.ts` (key = sku + size, `chaveDoItem`), `useCarrinhoOnline` adds each line's available stock (`disponivel`) so the checkout caps "+" and flags items that ran out; saved carts from before sizes drop shoe items without a size when the catalog arrives. "Compre de novo" sends shoes to the product page. POS: clicking a shoe opens `pdv/SeletorNumeracao` (pairs per size, colored; a zeroed size stays clickable because the register never refuses). The `Sidebar` is configured by props (`grupos`, `subtitulo`, `avisoDaRota` for badges, `status` for the footer block; search, tour and `onSair` only show when passed), so store-only state (`useCaixa`/`useAcoes`) stays in `MainLayout`. State lives in `ContaProvider` / `useConta()` (session + online cart in `fatec:carrinho-online`); totals in `hooks/useCarrinhoOnline.ts`. `MeusPontos` copies the level table from `regras.py`. Notifications: a bell in the client sidebar (`Sidebar` prop `notificacoes`) opens `pages/conta/PainelNotificacoes`; the list is computed from the painel by the pure `pages/conta/notificacoes.ts` (birthday, points expiring, products to review, close to the next level with the same 300-point cut as `acoes.PONTOS_PARA_SUBIR`, incomplete profile), nothing is stored in the DB. Each notification `id` changes when its situation changes, and `hooks/useNotificacoes` keeps the read ids per client in `fatec:notificacoes-lidas:<id>`. `/minha-conta/avaliacoes` (`Avaliacoes`, tabs "Para avaliar"/"Minhas avaliações", stars in `components/ui/Estrelas.tsx` with native radios, shared with the manager screen) lets the client review purchased products for points. `SaleDetailModal` takes `doCliente` to load from `/api/conta/compras/<id>/`. The landing only links to `/login` and `/cadastro`: store staff reach `/admin` by typing the URL. `MainLayout` is wrapped in `EquipeProvider` (`contexts/equipe.ts`, `useEquipe()`), which checks the staff session before mounting the caixa/ações providers and otherwise redirects to `/admin/entrar` (`pages/inicio/EntrarEquipe.tsx`, same `TelaAcesso` frame) with the requested page in `state.de`; the sidebar "Sair" ends the session. A 401 while resending the offline queue leaves the sales pending. Unknown URLs under `/admin` show `NotFound` inside the store layout; any other unknown URL redirects to `/`.
- The dashboard period lives in the URL (`?inicio=&fim=`), and so do the filters and page of the Clientes and Vendas lists. The Dashboard keeps its `PeriodFilter` and the CSV/PDF export buttons in a bar at the top of the page body (like the filters of Clientes and Vendas), not in the site header, and is organized in sections (Pontos, Vendas, Clientes). Its colors have fixed meanings (`pages/dashboard/tons.ts`): blue = points earned, green = redeemed, amber = cost/expiring, red = expired, violet = client base, cyan = sales; levels use bronze/prata/ouro (`components/ui/corDoNivel.ts`). "Exportar PDF" is just `window.print()` (`exportPdf.ts`): the paper layout is the `@media print` block at the end of `index.css` plus `print:` classes (sidebar, header and filter bar get `print:hidden`), and `useTemaClaroAoImprimir` forces the light theme while printing.
- First-visit guided tour: `MainLayout` opens `TourGuiado` (`components/layout/`, steps in `passosTour.ts`, state in `hooks/useTour.ts`) on the first visit to any app screen. It highlights each sidebar item (found by its `data-tour` attribute) and opens the mobile drawer by itself. Finishing or skipping saves `fatec:tour` in `localStorage`; the sidebar button "Rever o tour" reopens it. When a sidebar item or screen changes, update `passosTour.ts`.
- Screen logic lives in `hooks/`: `useCarrinho` (cart and totals), `useFilaVendas` (offline queue), `useAtalhosPdv` (F2/F10), `useAtalhoBusca` (Ctrl/⌘ K), `useSidebar` (open/closed, saved in `fatec:sidebar`) and `useCarregar` (loads from the API with loading/error/retry; `useDashboard` and the list screens use it). Pages only compose.
- `utils/` holds only pure functions used in 2+ places: `format.ts` (money, numbers, dates, `plural`, `normalizeText`) and `cpf.ts` (mask and validation, mirroring the backend `cpf.py`). A helper used by a single screen lives next to it (e.g. `pages/dashboard/csv.ts`, `todayLabel` in `MainLayout`); move it to `utils/` when a second place needs it.
- Both sidebars have "Como funcionam os pontos" (`Sidebar` prop `onAjuda`), which opens `components/layout/PainelAjuda` (`publico="cliente"` speaks to the client; `"loja"` adds register tips). Its numbers come from `regras.ts`.
- `regras.ts` mirrors the point rules of `regras.py` (100 points = R$ 5,00, tier table `NIVEIS`, validity, review points) for the POS previews and the explanations (`MeusPontos`, `PainelAjuda`); the backend is the source of truth. Change both together, with a test in `regras.test.ts`.
- Styling is Tailwind v4 (`@tailwindcss/vite`). Theme colors are CSS variables in `index.css` mapped with `@theme inline`, so `bg-surface`/`text-ink`/`border-line` switch to dark mode by themselves. Don't add `dark:` classes. The theme follows the system unless the user picks light/dark in the "Aparência e acessibilidade" panel (`components/layout/PainelAcessibilidade.tsx`, the single sidebar entry for theme, font size and accessibility options; theme logic in `hooks/useTema.ts`, saved in `fatec:tema`), which sets `data-theme` on `<html>`; an inline script in `index.html` applies it before the first paint. Each sidebar screen has its own color (`cor` in `navegacao.ts`). Besides the dashboard tones there are `rosa`, `laranja` and `esmeralda` tokens. Shared pieces are in `components/ui/` (`Button`, `Card`, `LevelBadge`, `Modal`, `Kbd`, `Pill`, `Led`, and form classes in `styles.ts`). Phones (checked down to 320px): tables mark less important columns with `colunaSecundaria` (hidden under 640px, on both `<th>` and `<td>`) and let long cells wrap with `quebraNoCelular`, so the key column (Saldo, Valor pago, Acumulado) stays visible; product grids switch to 2 columns under 520px. To vary a style, pick between whole class strings (see the `variant`/`tone` props) instead of appending a conflicting utility, because Tailwind doesn't guarantee which of two conflicting classes wins.
- `services/api/` is the only place that calls the API. `http.ts` holds `request` (CSRF, errors as `ApiError`), `errorMessage` and `queryString`; there is one module per area (`produtos`, `clientes`, `vendas`, `acoes`, `dashboard`, `conta`), each mapping the Portuguese API field names to the English names used in components (`nome` → `name`, `saldo_pontos` → `points`, …). Pages import from `services/api` (`index.ts`), which re-exports only the fetch functions, not the mappers. Add new endpoints to the module of their area with a mapper and export them in `index.ts`.
- Vite proxies `/api` to `API_URL` (`http://backend:8000` in Docker, `http://127.0.0.1:8000` otherwise, because on Windows `localhost` resolves to IPv6 and hangs through Docker Desktop).
- `config.ts` sets which register this POS is (`REGISTER_CODE`).

## Conventions

- Code written with AI help is marked with a `# Feito com IA: ...` / `// Feito com IA: ...` comment that explains the why (see `docs/onde-usamos-ia.pdf`). Keep this convention on AI-authored logic.
- Every rule in `regras.py`/`services.py` has a matching test. Keep that one-to-one coverage when rules change.
